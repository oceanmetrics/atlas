# S4 · Spatial uploads

> **Status in OceanMetrics Atlas (WP11, 2026-10-14).** A spike of the upstream MarineSensitivity app: which spatial upload formats to support and what each parser costs. The format list and rules it fixed are still the ones `src/lib/geo/upload/` implements (`docs/upload.md`); the Report that consumed uploads does not exist in OceanMetrics Atlas.


Verdict for spike S4 (`atlas-0 scaffold + spikes.md`, Step 4 / Deliverable 6). Raw measurements:
`spikes/4/RESULTS.md`. This verdict fixes **the format list atlas-6 implements** and the rules every
one of those formats has to pass through.

## The question

(a) What does each candidate parser cost when lazy-loaded — `shpjs` (zipped shapefile, reads `.prj`),
`@tmcw/togeojson` (KML/GPX), `flatgeobuf`, a WKT paste parser — and is each correct on five
committed fixtures (a Gulf rectangle; an Aleutian polygon crossing 180°; a multipolygon; a projected
UTM shapefile; a 40k-vertex coastline)? (b) Does DuckDB-WASM's `spatial` extension load at the
pinned version and `ST_Read` a registered `.gpkg`? If yes, GeoPackage is supported through it; if
not, `.gpkg` gets a friendly "convert to GeoJSON" message.

## Method

`spikes/4/` generates the five fixtures once in R (`sf` 1.1.2, GDAL 3.13.3, PROJ 9.5.1) in every
format its parser needs, together with an independently computed ground-truth manifest (vertex
counts, bboxes, first-ring shoelace sign, and the GDAL/PROJ reprojection of the UTM corners). The
Playwright specs never recompute that truth — they compare against it, and a deliberately corrupted
manifest is the seeded fault. Each parser is its own `import()`, so `scripts/lazy-bytes.mjs` can walk
one dynamic-import root's *static* graph and gzip it without another parser's bytes bleeding in.
Part (b) runs 5 fixtures × 2 DuckDB versions through `ST_Read`, plus a network spec that observes
worker traffic, blocks every non-localhost host (with a worker-fetch control proving the block is
live) and retries through a same-origin `custom_extension_repository`.

## The numbers the verdict rests on

**Cost per parser, lazy-loaded** (RESULTS § "(a) Bytes added per parser when lazy-loaded"):

| parser | gzip added | 40k-vertex parse | wire bytes for that fixture |
|---|---|---|---|
| `shpjs` 6.2.0 (zipped shapefile) | **46,708 B** | 15.9–21 ms | 373,367 B |
| `flatgeobuf` 4.4.0 | **11,375 B** | **2.3 ms** | 641,264 B |
| `@tmcw/togeojson` 7.1.2 (KML) | **3,804 B** | 38.0 ms | 1,053,861 B |
| hand-rolled WKT (`src/wkt.ts`, no npm dep) | **1,222 B** | 13.5 ms | 773,278 B |

All four are trivial against the 350 KB critical-path budget *as long as they stay dynamic imports*;
the 46.7 KB shapefile parser is the only one that would be felt if it ever went static.

**Correctness** (RESULTS § "(a) Per-fixture correctness per parser", 19/19 assertions pass against
the true manifest; 5 fail against the corrupted one):

- `gulf_rectangle` and `multipolygon`: all four parsers agree exactly with GDAL.
- `utm_zone`: **`shpjs` reprojects** from the `.prj` via its bundled proj4 to **0.000000 m** of the
  GDAL/PROJ truth. **`flatgeobuf` does not reproject** — its header carries the CRS correctly
  (`EPSG:32610`) and the reader hands back raw metres. The WKT parser has no CRS concept at all.
- `utm_zone_noprj` (the same shapefile bytes with only the `.prj` removed): `shpjs` returns
  `bbox [500000, 4300000, 520000, 4320000]` — **raw metres, silently**, with the captured browser
  console array literally `[]`: no warning, no error, nothing in-band for a UI to catch.
- `aleutian_dateline`: **none of the four parsers corrects for the antimeridian.** Every one reports
  the naive `[-177, 51, 178, 53]` — a **355°-wide** bbox where the truth is ~5°.
- Ring winding flips by **format, not parser**: `shpjs` reports CW (signed area −710) where
  togeojson/flatgeobuf/WKT report CCW (+710) for the same source ring. Confirmed with `ogrinfo` to be
  GDAL's ESRI-Shapefile **writer** storing the ring in reverse traversal order once it straddles
  ±180° — `shpjs` faithfully reports the bytes it was given.

**GeoPackage through DuckDB `spatial`** (RESULTS § "(b)" and § "Fix round 2, item 1"): all 10 cells
pass — `rowCount`, `bbox` and `vertexCount` exact against the manifest on **both** `1.32.0` and
`next`, `INSTALL spatial; LOAD spatial;` in 1180–2414 ms, `bundleUsed = eh`, `workerErrors = []`.
But it is not free and not local:

| | 1.32.0 | next (1.33.1-dev64.0) |
|---|---|---|
| host / path | `extensions.duckdb.org/v1.4.3/wasm_eh/spatial.duckdb_extension.wasm` | `…/v1.5.5/…` |
| bytes, first `.gpkg` drop | **23,469,719 (~22.4 MB)** | **23,602,613 (~22.5 MB)** |
| ms cold / after reload | 821–1,554 / ~50 | 769–1,328 / n.m. |
| every non-localhost host blocked | `LOAD spatial` **fails**: `Failed to execute 'send' on 'XMLHttpRequest': Failed to load '…'` | same |
| blocked + same-origin `custom_extension_repository` | **succeeds**, 449.8 ms, `ST_Read` still exact | not re-run (SQL setting, not version-specific) |

`ST_Read` behaves like every non-`shpjs` reader here: `utm_zone.gpkg` comes back as raw UTM metres,
not reprojected.

Two details that matter for the design: the extension load is an **explicit** `INSTALL`/`LOAD`, so
its failure is a clean, catchable SQL error — unlike S3's *implicit* `read_parquet` autoload, whose
blocked-network failure is an uncatchable `RuntimeError: function signature mismatch`. And the
22.4 MB is the *extension only*: atlas-2 already loads the DuckDB engine (~7.8 MB gzip for the `eh`
bundle) for the core data path, so `.gpkg` does not add an engine, only this file.

## What was NOT measured, and why it matters

- **GPX was never tested.** The subplan pairs "KML/GPX" under `@tmcw/togeojson` and only KML fixtures
  exist. `togeojson`'s GPX path is a different function on different XML; atlas-6 must add a GPX
  fixture before advertising the format.
- **GeoJSON — the format most users will actually drop — has no fixture either**, because it needs no
  parser. It still needs the same normalizer, and the same tests.
- **Chromium only, one machine, `eh` bundle only.** `selectBundle()` picked `eh` in every run, so the
  `mvp` platform's extension URL is untested on both spikes.
- **`custom_extension_repository` was tested same-origin (`localhost:4314`) only**, and only on
  `1.32.0`. Whether DuckDB's synchronous-XHR extension loader tolerates a *cross-origin* repository
  (e.g. the S3 bucket, which does answer CORS) is unmeasured, and it is the option that would matter
  if hosting size ever became a problem.
- **The reload measurement is an inference**: ~50 ms instead of ~800–1,580 ms for the same URL, with
  no `fromCache` flag observed. Nothing proves the 22 MB survives a *new session*, so the honest
  planning assumption is "22.4 MB per user, per browser profile, possibly per release deploy".
- **No malicious or malformed input was tested**: no zip bomb, no 500 MB shapefile, no `.gpkg` with
  many layers or a non-spatial table, no KML with network links. atlas-6 owns those.
- **Fixtures are synthetic** (including a deterministic "coastline"), single-feature, and all but one
  are WGS84. No multi-feature file, no file with attributes worth preserving, no curved geometry.
- **The original `createWorker()` hang was never isolated**, only fixed by matching S1's
  `new Worker(url)` wiring; whatever the underlying cause is, it is still there for anyone who uses
  the helper.

## Where DuckDB extensions are hosted — one rule, stated once

S3 and S4 hit the same mechanism, so the rule is one rule (S3.md rule 3 states the same thing):

> **The app self-hosts the extensions on its core data path, and only those.** `parquet` (3.0 MB, S3)
> is mirrored same-origin, keyed by DuckDB **engine** version, with
> `SET custom_extension_repository` set before the first query — it is needed in every session and
> its failure is an uncatchable WASM crash. `spatial` is **not** mirrored: it is 22.4 MB per platform
> per engine version (≈45 MB for `mvp`+`eh`, and again on every DuckDB bump), against a GitHub Pages
> site limit of 1 GB and a per-file git limit of 100 MB, all of it dead weight for the vast majority
> of sessions that never drop a `.gpkg`. It is fetched from `extensions.duckdb.org` on demand,
> behind explicit user consent, and its failure degrades to a message.

No geometry leaves the browser either way — the transfer is inbound only, the user's file is never
uploaded — but the `.gpkg` path does make a **third-party request** the rest of the app never makes,
and the user is told so before it happens.

## Consequences — rules atlas-6 inherits

1. **The format list.** First class: **GeoJSON** (native, no parser), **zipped shapefile** (`shpjs`),
   **KML and GPX** (`@tmcw/togeojson`, GPX pending a fixture), **FlatGeobuf** (`flatgeobuf`), and
   **pasted WKT** (hand-rolled parser kept in `src/lib/geo/`, not a dependency — 1.2 KB and fully
   under our own tests). Best effort: **GeoPackage**, per rule 2.
2. **GeoPackage is supported, but never silently.** Dropping a `.gpkg` prompts once: this format needs
   a one-time ~22 MB download from `extensions.duckdb.org` (a third party), with "convert to GeoJSON
   or FlatGeobuf instead" offered alongside. On decline, or on any `INSTALL`/`LOAD` failure (blocked
   host, ad-blocker, corporate DNS — measured, with the exact error text), fall back to the friendly
   "convert to GeoJSON" message. Load it lazily, only on a `.gpkg`, and never on the first-paint path.
3. **Every parser output passes through exactly one normalizer** — an exported function in
   `src/lib/geo/`, called by the UI, asserted by tests — that does the three things *no* parser does:
   - **Reject projected coordinates.** If the source carries a CRS (shapefile `.prj`, `.fgb` header,
     `ST_Read`'s layer CRS) and it is not EPSG:4326/CRS84, reproject with proj4 before anything else;
     `shpjs` already does this correctly, `flatgeobuf` and `ST_Read` do not, so the normalizer must,
     not the parser. If the source carries **no** CRS (a `.prj`-less zip, pasted WKT, bare GeoJSON),
     test the coordinate ranges: any |x| > 180 or |y| > 90 cannot be degrees → **refuse the file** and
     tell the user, naming it: "this file looks like projected coordinates in metres and carries no
     coordinate system (`utm_zone_noprj.zip`: x up to 520000); re-export as WGS84 / EPSG:4326, or
     include the `.prj`". Never score it. Record the residual gap honestly in the code comment: a
     projected file whose values happen to fall inside ±180/±90 still passes this test, so the CRS,
     when present, is always authoritative over the range check.
   - **Rewind rings.** Normalize to RFC 7946 (exterior CCW, holes CW) before any area, coverage or
     codec work, because GDAL's shapefile writer reversed the winding of the dateline fixture
     relative to the same geometry in KML/FlatGeobuf/WKT. No downstream code may read meaning from
     the input's ring order, and the shoelace sign is only computed *after* normalization.
   - **Handle the antimeridian.** All four parsers return a 355°-wide bbox for a 5°-wide Aleutian
     polygon. A naive bbox is what a tile fetch plan and the D8 places codec would use, so a
     355°-wide box means fetching the whole grid. Compute a dateline-aware bbox (split at ±180 or
     work in a shifted 0–360 frame) in the normalizer, and unit-test it against the Aleutian fixture.
4. **`shpjs`'s silence is the interface contract.** A `.prj`-less shapefile produces plausible,
   silently wrong numbers with no console output at all — so the CRS check is a *gate in our code*,
   never a hope that the parser will warn.
5. **Keep every parser a dynamic `import()`.** `shp*` is already on the size budget's forbidden-static
   list; `flatgeobuf`, `@tmcw/togeojson` and the WKT parser should join it when atlas-6 wires them.
6. **Never use duckdb-wasm's `createWorker()`** — `new Worker(bundle.mainWorker)`, same-origin, as S1
   and this spike both concluded the hard way.
7. **Fixtures: move them, don't copy them.** The 3.9 MB in `spikes/4/fixtures/` (of which ~3.5 MB is
   the 40k-vertex coastline in five formats) is the ground truth atlas-6's tests need, and it must not
   exist twice. atlas-6 starts by `git mv`-ing `spikes/4/fixtures/` to
   `tests/fixtures/spatial-uploads/` — the generator (`generate_fixtures.R`), the manifest and the
   faulty manifest travel with it — because `tests/fixtures/` is where this repo's pyramid puts
   fixtures and `spikes/` is archived at the plan's close-out. They are test inputs only: nothing
   under `tests/` reaches `dist/`, so the size budget is unaffected.
   *(Done in atlas-6 step 3, 0.8.1, at `tests/fixtures/upload/` rather than the name guessed here;
   a plain GeoJSON, a closed-track GPX and an open-track GPX joined them. See `docs/upload.md`.)*

Client-side COG display is decided in `S3.md` (no); S4 does not bear on it.

**Verdict:** atlas-6 implements GeoJSON (native), zipped shapefile, KML/GPX, FlatGeobuf and pasted
WKT as first-class uploads, and GeoPackage only as a consented best-effort path — `spatial` loads and
`ST_Read`s all five fixtures exactly on both DuckDB versions, but costs a one-time ~22.4 MB
third-party download that fails when `extensions.duckdb.org` is blocked, so it is prompted, lazy, not
mirrored, and falls back to "convert to GeoJSON" — with every format passing through one normalizer
that rejects projected coordinates, rewinds rings to RFC 7946 and computes a dateline-aware bbox,
because no parser measured here does any of the three; pins: `shpjs@6.2.0`,
`@tmcw/togeojson@7.1.2`, `flatgeobuf@4.4.0` (WKT stays hand-rolled, no dependency).
