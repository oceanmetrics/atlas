# S2 · First paint without WASM (and the maplibre-gl pin)

> **Status in OceanMetrics Atlas (WP11, 2026-10-14).** A spike of the upstream MarineSensitivity app (maplibre-gl 6.10 worker wiring, vector rendering with the worker). The conclusion about the worker and `queryRenderedFeatures` still guards the `maplibre-gl` pin; mentions of the Report and Program Area layers are upstream.


Verdict for spike S2 (`atlas-0 scaffold + spikes.md`, Step 4 / Deliverable 6). Raw measurements:
`spikes/2/RESULTS.md`; the committed gate is `spikes/2/e2e/s2.spike.spec.ts` with its seeded fault
page `spikes/2/fault-worker-url.html`. Two things are settled here: whether tier 0 really paints
with zero DuckDB bytes, and which `maplibre-gl` version **and wiring** the app is built on — which
is a **security** decision as much as a build one.

**Read the numbers with their version attached.** The harness moved from `maplibre-gl ^5.24.0`
(round 1) to the pinned `^6.10.0` with `?worker&url` (round 2/3), and `titiler-v8` was unreachable
06:02–08:50Z on 2026-09-21 (the project server lost its network and was rebooted), which is why the
5.24 and 6.10 timing tables were taken in different sessions. The raster-dependent half has since
been re-run on the pinned version — see "Timing, re-measured on the pinned version" below.

## The question

Does the shell + MapLibre + the v7 zones PMTiles + one score COG through titiler, fed only by
`manifest.json` (+ a stubbed `boot.json`), reach a real first paint within **2.5 s with zero DuckDB
bytes requested**? And: does `maplibre-gl` 6.x work under Vite 8, or must the app pin `<6` the way
CalCOFI Explorer did (`atlas-refs/calcofi explore review.md` §11 lesson 10)?

## Method

`spikes/2/` builds the shell against the real v7 manifest (zones PMTiles `programarea_2026-01`,
score COG `…/cog/usa05/d20874edf0c43166.tif`, `rescale 0–90`, `spectral_r`) with 20 real
Program-Area scores and one zone's 8 rescaled components in `public/boot.json`. The gate is **split
in two** (RESULTS § "Fix round 3"), because the pin's own claim and the timing budget depend on
different things:

- **S2 VECTOR GATE** (`?seed=vector-only`, a style with the zones vector source and **no** raster
  source): asserts `queryRenderedFeatures` on `zones-line`, zero 404s on any
  `maplibre-gl-worker`/`maplibre-gl-shared` response, zero duckdb/wasm requests, and the table and
  flower rendered. Needs S3 only, so it always runs.
- **S2 RASTER + TIMING GATE**: the two ocean-point `gl.readPixels` probes and
  `firstDataFrame <= 2500 ms`. `test.skip()`-ed with a named reason from a one-shot titiler
  reachability probe, so an outage reports **SKIPPED**, never a false pass and never a 30 s timeout.

Timings come from `scripts/measure.mjs`: fresh browser process, fresh context, HTTP cache disabled
via CDP, cross-origin bytes from `Network.loadingFinished.encodedDataLength`.

## The numbers the verdict rests on

### Verified on the pinned version (`maplibre-gl ^6.10.0`, `?worker&url`)

RESULTS § "Corrected: S2 VECTOR GATE + RASTER/TIMING GATE + four self-pinned seeded faults" —
`npm run e2e` in `spikes/2` exits **0** with **4 passed / 2 skipped**, reproduced twice:

- `zones-line` `queryRenderedFeatures` = **10** features (20 in the archive, 10 in the default
  `center [-96,38], zoom 3` viewport), **zero** worker/shared 404s, **zero** duckdb/wasm requests.
- The two titiler-dependent tests report SKIPPED with the probe's reason
  (`reachable=false … operation was aborted due to timeout`).
- Seeded faults that ran and passed as faults: `?seed=duckdb-fetch` (trips the zero-duckdb
  assertion), `?seed=blank-style` (trips the painted-pixel assertion), and `fault-worker-url.html`
  (the `?url` wiring) — each now asserts its own trigger with a real `expect()` **before** the
  assertion that must fail, so it cannot pass for the wrong reason.
- **The `?url` correction is committed and reproducible** (RESULTS § "Regression check: swapping
  `?worker&url` for `?url` in the MAIN entry turns VECTOR GATE red"): with `?url`,
  `dist/assets/maplibre-gl-worker-CupLwWe3.mjs` (19,007 B) is emitted verbatim and its own
  `./maplibre-gl-shared.mjs` import **404s**, `zonesFeatureCount` is exactly **0**, and the gate
  fails in 10.4 s with a message naming source `"zones"`, layer `"zones-line"` and the 404. With
  `?worker&url` the worker is self-contained (`maplibre-gl-worker-CNLXcz58.js`, **508,485 B raw /
  143,867 B gzip**, shared chunk inlined, no second runtime request) and the gate is green.
- **4-cell matrix** (RESULTS § "Corrected 4-cell matrix (fix round 2)"): `vite dev` and
  `vite build`+`preview`, with and without `optimizeDeps.exclude` — all four start with no
  `pageerror`, all four render **10** vector features, none has a worker/shared 404, and the two
  build cells are byte-identical, confirming `optimizeDeps.exclude` is dev-only.
- **Critical path, 6.10, committed config**, computed with the same `zlib.gzipSync(level 9)` the
  budget script uses: app chunk 277,637 B + CSS 10,384 B + entry wrapper 128 B = **288,149 B gzip
  (281.4 KiB)** against the 350 KB static budget. The worker's 143,867 B gzip is **not** in that
  number: it is a runtime `new Worker(url)` asset, and the root checker now gives it its own
  `RUNTIME_WORKER_BUDGET_BYTES` = 150 KB (F3) — **9,733 B, 6.3 %, of headroom**.
- **`firstDataFrame` on 6.10: one clean sample, 795.3 ms** (build + preview, with exclude), captured
  just before the outage began; `zonesPainted` 603.8–613.6 ms in that cell and 457.3–861.7 ms across
  dev cells during the outage (RESULTS § "Timing table (fix round 2 …)"). Superseded as the basis of
  the timing claim by the two N=9 samples below.

### Timing, re-measured on the pinned version (orchestrator, 2026-09-21 ~09:05–09:20Z)

Once the server returned at 08:50Z, the orchestrator re-ran `npm run measure` against the pinned
6.10 harness (`vite build` + `preview`, fresh browser process + fresh context + cache disabled per
run), **N = 9 twice, ten minutes apart**:

| | FCP median | `firstDataFrame` median | `zonesPainted` median | `idle` median |
|---|---|---|---|---|
| sample A (N=9) | 36.0 ms [28.0, 92.0] | **740.3 ms** [622.3, 1135.2] | 715.4 ms [489.8, 887.0] | 1380.4 ms [1305.9, 2032.0] |
| sample B (N=9) | 36.0 ms [28.0, 56.0] | **662.2 ms** [568.0, 944.8] | 557.3 ms [453.2, 945.8] | 1267.4 ms [1218.7, 1430.9] |

Cross-origin cost, sample A: before `firstDataFrame` 6 S3 requests / 29,916 B and 20 titiler
requests / 35,668 B; before `idle` 6 S3 / 29,916 B and 28 titiler / 62,354 B — the same shape as the
5.24 round.

**All 18 of 18 cold standalone runs are under 1.2 s against the 2.5 s budget, on the pinned
version.** The 2.5 s question is therefore answered for 6.10, standalone.

**But the same metric is flaky inside the parallel suite.** `npm run e2e` (6 specs across parallel
Playwright workers) passed 6/0 on the first run after the server returned — the RASTER + TIMING gate
and the 3 s-delay fault both execute now — and then, over five more unmodified runs, `firstDataFrame`
read **3125.2 ms** and **3783.4 ms** (two runs **failed** the 2.5 s gate), 1584.6 ms, and two
passes; in one run the 3 s-delay fault hit its own 20 s wall-clock wait instead of failing on the
budget assertion. The orchestrator's seeded fault (budget 2500 → 300 ms on the main gate) went red
reading a real number ("firstDataFrame was 1584.6ms"), so the gate itself is sound. **The finding, no
further:** this metric is dominated by titiler tile latency and by contention — six specs sharing
one titiler and one software GL renderer at once — so it is 3–4× under budget standalone and
unreliable in parallel.

### From the superseded `^5.24.0` round, not the pinned version

RESULTS § "Timing table (round 1, `maplibre-gl ^5.24.0` … now superseded)", N=9 cold runs: FCP
median 24.0 ms; **`firstDataFrame` median 499.1 ms, range 467.8–573.9 ms**; `zonesPainted` median
456.3 ms; `idle` median 1078.2 ms; 6 S3 requests / ~30 KB and 28 titiler requests / ~62.3 KB by

### The advisory (version-independent)

RESULTS § "npm audit — precise advisory facts", cross-checked against GitHub's advisory record and
independently verified by the orchestrator: `GHSA-jrc7-96c5-q579` (CVE-2026-85061), **critical,
CVSS 3.1 = 10.0**, "XSS sanitizer bypass in `DOM.sanitize()`", `vulnerable_version_range`
**`<= 6.4.0`**, `first_patched_version` **`6.4.1`**. All **35** published 5.x releases (5.0.0 …
5.24.0) are inside that range; **no 5.x release is or will be patched.** npm `latest` is 6.10.0.
Separately, 6.x has **no default export**: a default import is a dev-time `SyntaxError` and a hard
Rolldown `[MISSING_EXPORT]` build failure (RESULTS § "Round 0's (superseded) … findings").

## What was NOT measured, and why it matters

- **The gate was never run on the CI runner**, which is what the subplan's wording requires; every
  timing here is this laptop and this network.
- **No timing number survives contention.** The two N=9 samples are standalone runs; the same gate
  inside the parallel suite failed 2 of 6 runs. Nothing here measures how the budget behaves under a
  loaded CI runner, which is the environment the subplan actually names.
- **Chromium only, headless, swiftshader.** No WebKit or Firefox first-paint numbers, no phone
  viewport, no throttled network, no cold DNS/TLS.
- **The degraded path is now the *observed* state, not a hypothesis, and is still untested as a
  design.** Through the 06:02–08:50Z outage the vector zones, the table and the flower all rendered
  correctly while the raster never arrived. That is exactly the behaviour the plan's Risks section
  promises, and nothing in the app asserts it: atlas-8 owes a spec that asserts the degraded view
  rather than skipping it.
- **6.10 was exercised in one page's shape only**: one raster source, one PMTiles vector source, one
  `setStyle(diff:true)`. Not exercised: terrain, globe, the RTL-text plugin, custom layers,
  `addImage`, or popups — which is precisely where the sanitizer advisory lives. `^6.10.0` admits
  future 6.x releases nobody has run.
- **No exploit was attempted** for GHSA-jrc7-96c5-q579; the decision rests on the published range and
  patch, not on a demonstration.
- **The worker's 6.3 % headroom under the 150 KB runtime budget is a measurement of one version.** A
  maplibre patch that grows the worker by ~10 KB turns that budget red, which is the intended
  behaviour but will read as a surprise.

## The security decision, stated plainly

The subplan's written fallback — "if dev or build breaks, pin `^5.24` and say so" — is **rejected**.
It would knowingly ship a critical (CVSS 10.0) advisory with no patched release in the 5.x line, for
the life of the app, to avoid a build problem that turns out to be one query-parameter wide. 6.10.0
is the patched line *and* it works under Vite 8 — but only with a specific wiring, and the pin is
worth nothing without it. **The pin depends on:** named imports (no default export exists),
`import workerUrl from "maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url"` followed by
`setWorkerUrl(workerUrl)`, and a gate that asserts a *vector feature rendered* — because `?url`
produces a build that paints rasters and silently renders no vector data at all.

## Consequences — rules later phases inherit

1. **`maplibre-gl` at `^6.10.0`** (caret, so a patch for the next advisory lands without a plan
   change; the lockfile still pins the exact build for `npm ci`). Never `<6`.
2. **Import it named**, e.g. `import { Map, addProtocol, setWorkerUrl, type StyleSpecification } from
   "maplibre-gl"`. A default import is a hard build failure in 6.x, not a style preference.
3. **Worker wiring (atlas-2/3):** `import maplibreWorkerUrl from
   "maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url"; setWorkerUrl(maplibreWorkerUrl);` — the
   `worker` part is load-bearing.
4. **Any map spec must assert a rendered vector feature** — `map.isSourceLoaded(id)` **and**
   `map.queryRenderedFeatures({ layers: [...] }).length > 0`, with the failure message naming the
   layer — plus zero 404s on worker/shared assets. Raster tiles paint with a dead worker, so a
   `gl.readPixels` gate alone is not a check. Copy the split from
   `spikes/2/e2e/s2.spike.spec.ts`: the vector assertion must not depend on titiler.
5. **`canvasContextAttributes: { preserveDrawingBuffer: true }`** on the `Map` constructor. The bare
   top-level key is silently ignored in 5.x/6.x and every out-of-process `readPixels` then reads
   `(0,0,0,0)` while the map visibly renders.
6. **`map.resize()` immediately after construction.** Without it, raster tile requests were
   non-deterministic under headless Chromium.
7. **Do not add `maplibre-gl` to `optimizeDeps.exclude`.** 6.10 works with and without it in dev, and
   the build output is byte-identical either way; the exclude list stays for `@duckdb/duckdb-wasm`.
8. **Compose one style, apply with `setStyle(style, { diff: true })`** (lesson 3); this spike's
   harness is the working example.
9. **First paint may not depend on the worker or on titiler**, and the app must *render* the
   titiler-down state rather than wait on it — the outage during this spike is the proof that state
   is real.
10. **Budget:** the static critical path is 288,149 B gzip of 350 KB with maplibre + pmtiles + CSS
    alone, leaving ~70 KB for app code; the worker sits at 143,867 B of its own 150 KB runtime budget
    (F3), 6.3 % spare. Both numbers are per-version and must be re-read after any maplibre bump.
11. **`page.waitForFunction(fn, arg, options)` takes options THIRD.** The two-argument form silently
    falls back to the 30 s default — it was never bounded (RESULTS § "The `page.waitForFunction`
    arity bug"). Pass `undefined` as the second argument in every spec in this repo.
12. **The timing gate runs alone (atlas-8).** Give it its own Playwright project with `workers: 1`
    and no other spec touching titiler in the same run — measured: 2 of 6 parallel runs failed the
    same budget that 18 of 18 standalone runs cleared by 3–4×.
13. **Report a median over N ≥ 9, never a single sample (atlas-8).** One run of this metric says
    nothing: the two standalone samples' own ranges reach 1135.2 ms and 944.8 ms around medians of
    740.3 and 662.2 ms.
14. **The 3 s-delay fault must assert on the budget, not on a wall-clock wait (atlas-8).** In one
    observed run it hit its own 20 s wait timeout instead of failing the 2500 ms assertion — a fault
    that fails for the wrong reason is not a proof the gate can fail.

Client-side COG display is decided in `S3.md` (no); this spike's relevance is only that titiler is on
the first-paint path and its outage mode is now observed but still unasserted.

**Verdict:** `maplibre-gl` 6.x is adopted over the subplan's `^5.24` fallback because no 5.x release
escapes the critical advisory GHSA-jrc7-96c5-q579, and on the pinned version both halves are now
proven — the committed VECTOR GATE renders 10 `zones-line` features with zero worker/shared 404s and
zero DuckDB bytes in all four dev/build × exclude cells, and first paint clears the 2.5 s budget in
18 of 18 cold standalone runs (`firstDataFrame` medians 740.3 ms and 662.2 ms over two N=9 samples)
— with two things still open: the same gate is flaky inside the parallel suite (2 of 6 runs over
budget, titiler latency and contention, so atlas-8 must run it alone, median over N ≥ 9, with the
3 s-delay fault asserting on the budget rather than a wall-clock wait) and it has never run on the
CI runner; the pin holds only with named imports, `?worker&url` + `setWorkerUrl`, and a
vector-feature assertion in the gate; pins: `maplibre-gl@^6.10.0`.
